# THE MARKET: an outside review (1 Nov 2026)

Three parts, as the owner asked: (1) the game as a professional reviewer sees it, (2) the defence of why it is built this way, (3) the verdict: what to keep and what to change, honestly, ranked by payoff. Numbers are from this checkout (`main` at 97f1837), the built `dist/g/`, `docs/perf-audit.md`, and screenshots taken in software rendering (so only draw and triangle counts are absolute; milliseconds are relative).

## Part 1: the outside review

### 1. Shape of the code

| measure | value |
|---|---|
| source files in `src/` | 260, numbered, joined in order into one page |
| source size | 3.9 MB, 27,851 lines, 138 characters a line on average |
| lines over 400 chars / over 1,000 chars | 302 / 39 |
| `frame()` in 075-main-13 | one function, 13 KB, 305 statements on 55 lines |
| global registries declared empty in 003b-systems and filled later | 100+ (`ROOMS`, `UI`, `LITE`, …) |
| `window.X=` globals | 273 |
| `SHARED.*` references | 1,262 (37 distinct keys) |
| hash/noise helpers re-defined per file | 25 |
| runtime-painted canvases / CanvasTextures | 81 / 61 |
| `new THREE.Mesh` / `InstancedMesh` / `BatchedMesh` | 528 / 81 / 1 |
| `onBeforeCompile` sites / global `ShaderLib` string patches | 47 / ~8 (fog, mist, lambert, peek, clipping, shadows) |
| three.js | 0.160.0, pinned |

**What a reviewer sees.** This is a 28,000-line single-page game written as one concatenated module with a home-made module system: every file is a real ES module on disk, but the build blanks the import/export lines and joins the files, so at run time it is one scope. Cross-file needs are solved by declaring ~100 empty objects up front and `Object.assign`-ing into them later. The code is written in an extremely dense style (whole systems on one line) with almost no comments by rule. It is consistent, it builds, and it has a dependency checker (`tools/imports.cjs`, `tools/scope.cjs`) that stops a file reading a name from a later file. But it is not code a new human engineer can read; it is code an AI agent and a strict build check can maintain. The frame function alone has 56 inline `SYS.go` wrappers and 17 phases interleaved with direct calls, which contradicts the repo's own rule ("per-frame work a SYS entry, never a wrapper") and is where ordering bugs will hide.

### 2. Build and loading

| what the first visit downloads (gzip) | KB |
|---|---|
| shell `market.html` | 0.2 |
| `m.<hash>.js` (the game's own start code: 2.3 MB minified) | 848 |
| `c.57fc…js` (three.js r160) | 171 |
| `rig.<hash>.js` (the Walker's rig) | 45 |
| start data (bases, characters, creatures, forest, guardians, hero, items, kit, pawns, props, raincat, textures, trees, world) | ~660 |
| **first frame total** | **~1.7 MB** |
| `x-later.js`, fetched right after the start | 257 |
| `nav.<hash>.js` (recast, when navigation first loads) | 234 |
| lazy data (fishes 1,017; rpgchars 354; toons 341; skel 104; dragon 26; fish 31) | ~1.9 MB, only when used |

The build is a Python script plus five Node tools that between them do what a bundler does: import ordering, yield insertion (`tools/yields.cjs` puts an `await` breath every 40 ms of top-level work so the page never freezes), function-level code splitting by `'@name'` markers (`tools/chunks.cjs`), an automatically found "code the start never runs" chunk (`tools/later.cjs`, 691 functions), base64-to-binary splitting of the data files, content-hashed names and immutable caching. Models are Int16-quantized positions, Uint8 colours and Int16 quaternion clips in JSON, decoded by 30 lines of code. There is no glTF, Draco, KTX2 or texture loader; almost every texture is painted at start with 2D canvas code. The start takes ~23 s in software rendering here (not a real-world number); it is spread over hundreds of breaths so the tab stays responsive.

**Reviewer's take.** The data format is genuinely small and fast to decode; the chunking and the "later" chunk are smart. But the game's own start code is 2.3 MB minified (848 KB gz), five times three.js itself, and the browser parses and compiles all of it before the first frame. `tools/later.cjs` already uses Chromium's precise coverage over one scripted start (fresh start, the street, the park and back), but it marks only free functions of 300+ characters; methods, small functions, `this` arrows and everything that one route happened to touch stay in the start bundle. Measured here (`tests/startprof.cjs`, software rendering, so only the shape counts): 27.8 s to `__started`, with 40 long tasks, two of them before the start totalling 11.7 s and the longest single task 9.2 s, so the breath inserter does not reach everything. Two small drifts: CLAUDE.md names the bundle `game.<hash>.js` but `tools/bundle.cjs` writes `m.<hash>.js`; and a `__DATA__` read inside the `'@guide'` function is inlined into its chunk, so `x-guide.js` is 310 KB of data that should have been two hashed JSON files. Painting 61 textures and several 2048-wide atlases on the CPU at every start is the price of the small download; nothing is cached between visits except HTTP.

### 3. Rendering

- One `WebGLRenderer`, no antialiasing, pixel ratio 1, canvas at 0.866 of the window (the rounded frame), **internal resolution = native by default** (`RESI` 4, HIGHEST).
- Post chain: RenderPass → distance fog (reads a depth texture) → Walker outline (a float ID buffer, when on) → OutputPass (folded into the previous pass) → LOOK (glow in two half-res blurs, night grade) → **PS2 filter (always on, last): box-filters the picture into a 427×240 cell grid, 15-bit colour, YIQ bleed, grain.**
- Extra renders a frame when near them: the whole scene again for water refraction (`WATER.under`, `RIVER.pre`, at canvas size), the skyline blur, the Walker's 512² self-shadow, two NPCs' 256² self-shadows (51 such targets allocated), the water ripple ping-pong, the 192² flow sim.
- Shadows: three sun directional maps (1536² static, 1024² moving, 1024² far) updated on change, not every frame; one point-light cube shadow (512) from a pool of 8 nearest lamps; `BasicShadowMap`, 4-tap PCF patched in.
- Materials: Lambert for the world with a global shader patch (fixed face tones, AO, wetness, sun beams, cel bands), Toon with gradient maps for characters, 89–95 shader programs in play.
- Culling: VIS (hide with reasons), LEVELS (other levels hidden), CULL (big meshes and instanced meshes cut into 10-tile cells, nothing past the haze drawn), PERFX (room interiors split into per-room child meshes shown only inside; batches chunked into 16-tile cells; NPCs in other rooms hidden), NPCs frustum + 25-tile distance + 10 fps animation gating with rest.
- Measured (perf-audit, after its fixes): street by day 410 draws, 410K triangles a frame (main pass ~300K, the lamp cube ~180K); night 124 draws, 291K; the stated budget is 100K on screen.

**Reviewer's take.** The culling story is unusually complete for a hobby engine. The expensive thing is structural: **the frame is shaded at native resolution (about 1.4 M pixels at 1080p) and then thrown away into 102K PS2 cells.** Every full-screen pass, the fog's depth read, the float outline buffer and the water's second scene render all pay native fill rate for a 240-line result. The lamp's six-face cube shadow is the other big fixed cost. The toon/lambert split with hand-patched `ShaderLib` strings means three.js can never be upgraded without rewriting the patches (the `SHX` watcher at least reports when a patch misses).

### 4. Gameplay systems and the frame

- Variable timestep for the player (dt clamped to 50 ms); fixed 1/120 s substeps for loose things and the Rapier ragdoll; 1/180 s for water.
- Player collision: a circle against a flat list of AABBs (`SHARED.solids`), scanned whole every frame. NPC push, online push.
- Characters: one path (`makeNPC`, SkinnedMesh + AnimationMixer, clips at 12 fps baked), the Walker on a procedural rig with rigid pieces. Pathing: A* with recast in a worker.
- Places: each a `grab()` builder; insides off the map built on entry behind a fade and dropped on exit; the world as blocks. Sections exist in `data/world.json` with a grid and ids; only A is built.
- Owned state (cash, inventory, apartment, skills) in one `/owned` key-value store on a Durable Object; position and settings in localStorage.

**Reviewer's take.** The place/room architecture (blocks outside, off-map insides, one `ROOMS.part`/`unpart` pair) is the best-designed part of the game: it is what lets 40 places coexist at 100–400K triangles. The sections scaffold is right-sized. The player loop is a wall of special cases (boat, ride, swim in five waters, ladder, climbs, FEEL controller, ragdoll) in one function.

### 5. Multiplayer and the server

- One Cloudflare Worker serves the site and gates everything on a Supabase JWT in a cookie (checked against Supabase, cached 5 min). One `Block` Durable Object per section relays `mv` (6 Hz), `me`, `act`, `ps`, `hit`, `grab`, `say`, `world`; the client interpolates 160 ms behind, no extrapolation, draws the nearest 20 within 60 tiles.
- The server clamps and rate-limits but simulates nothing: positions, hp, death, hits (judged by the attacker, applied by the target), cash and inventory (opaque strings in `/owned`) are all client-reported. Any player can write any `world` key. No player cap per Block, `hibernate:false`.
- Secrets are not in the repo; the publishable key is (fine). The session cookie is set by JS and is not HttpOnly. Two routes (`/now`, image proxies) are unauthenticated. partysocket and supabase-js are loaded from a CDN without integrity hashes.
- Supabase tables for players, admins, invite codes and bug reports have no SQL in the repo, so their row-level security cannot be reviewed here.

**Reviewer's take.** Right design for a small invite-only world: cheap, one DO per section, nothing to scale yet. Wrong design the moment money matters: the economy ($1,000,000 to start, every shop and the apartment's furniture paid from a client-held number) is trivially editable by any logged-in player, and nothing on the server would notice.

### 6. Tests and CI

- 141 test scripts (4,270 lines): 134 drive the built page in headless Chromium under SwiftShader (88 of them take screenshots), 7 read the rig out of a readable build under plain Node. No test runner; each script is its own process.
- On a pull request: build, `core`, `site` (the real worker under `wrangler dev`), `places`, plus whichever extra checks the changed files map to. The measuring checks (triangle budget, same picture, same pixels) run only with a label; nothing runs on `main` after merge. The owner chose this ("not as check heavy").
- Commit cadence: 94–162 commits a day over the last four days, nearly all by AI sessions, merged through pull requests.

**Reviewer's take.** The tests are almost all integration tests, and each costs 20–90 s of software rendering, which is why they have to be rationed. Performance regressions are invisible between the rare measured runs; a 50% triangle regression merges green. The seven Node-only checks show the fast path exists, but the core logic (collision, ZONES, SYS order, the SKIN decoder, the online interpolation) still needs a browser to be tested.

### 7. Process and documentation

`docs/HISTORY.md` (5,100 lines, 336 dated decisions) and `docs/MAP.md` (generated) are the memory of the project; CLAUDE.md is a real engineering rulebook (one path, mechanic not instance, cost stated, owner decides). This is far better project hygiene than most indie codebases. Its weakness is that the rules are enforced by reading, not by tooling, except the import order.

## Part 2: the defence (why it is built like this)

1. **One owner, many AI sessions, shipping several times a day.** Every structural choice follows from that. Numbered files in one order, one name per system, "declared empty up front" registries and `grab()` builders mean a session can add a place by adding one file with no edits elsewhere, and parallel branches rarely conflict. The dense one-line style and the no-comments rule exist because the owner reads diffs and decisions, not source; the minifier strips comments anyway.
2. **"Smallest download" and "render only what's needed" were set as rules on 17–18 Oct.** Painting textures at start, Int16 JSON models, the breath inserter, the `later` chunk and the data split all serve the first: a whole city with 40 places in 1.7 MB is a real achievement; a glTF/KTX2 pipeline would be 3–10× that for this look. The culling layers (VIS, CULL, PERFX, LEVELS, haze cut, room split) serve the second and were each added against a measured number in `perf-audit.md`.
3. **The home-made module system is a dependency rule, not a bundler substitute.** It forces a file to read only from files before it, which makes the 260-file order a true topological order and makes "where does this come from" answerable by `docs/MAP.md`. esbuild still does the minifying and the website bundling; the tools only own what esbuild cannot check (order, scope, chunks by marker).
4. **Rendering at native resolution and then PS2-filtering is a decision trail, not an oversight.** On 27 Oct the owner first asked for "no pixelation, sharpest only", then the same day picked the PS2 filter as the look, then asked for RESOLUTION back with HIGHEST as the default. The code implements exactly those three decisions in that order.
5. **Client authority is correct for a beta of friends with invite codes.** Server simulation of movement, combat or an economy is a large standing cost in code and in Durable Object CPU; the owner has explicitly deferred it ("scaffold the future, don't build it early"). The relay is already shaped for authority (one DO per section, server-stamped positions on `hit`, `held` tracked server-side for grab/toss).
6. **Pinning three.js r160 and patching `ShaderLib` by string replace** is what lets one Lambert program carry the whole world's look (face tones, AO, wet, cel bands, fog in 8 steps) with 89–95 programs instead of hundreds of custom `ShaderMaterial`s; the `SHX` watcher turns a silent miss into a console warning.
7. **Integration tests only** because the thing that breaks here is the picture and the place, not a pure function; a screenshot test catches "the wall is half missing", a unit test does not. The owner asked for checks to be light after Actions minutes ran out (28 Oct).

## Part 3: the verdict

Keep the architecture. It is coherent, every odd choice has a measured reason, and rewriting a 28,000-line game that ships daily would cost months and lose the owner's decision trail. The changes worth making are the ones below, in payoff order. Each stays inside the repo's own rules; none of the five under A changes what the owner sees.

### A. Do these (high payoff, low risk, no look change)

1. **Render at 480 lines when the PS2 filter is on.** The filter reads a 2×2 box of texels per 240-line cell, so a 480-line internal frame gives the identical picture to a native one while shading 4–5× fewer pixels at 1080p and 9× fewer at 1440p; every post pass, the fog depth read, the outline float buffer, the LOOK blurs and the water's second scene render shrink with it. Screenshots of the station at `?res=2` and `?res=4` through the filter are the same picture (taken for this review; `tests/samepic.cjs` can prove it on any change). Mechanically: the internal size follows the filter's line count ×2 while PS2 is on; HIGHEST keeps its meaning when the filter is off. This touches a decision (HIGHEST the default, 27 Oct), so it needs the owner's word, but it is "the same picture for less", which is the rule he set on 25 Oct.
2. **Cache the painted atlases and textures between visits.** The start repaints 61 textures and the batch atlases on the CPU every load. Storing the finished atlas pages in the Cache API keyed by the build hash (a new build repaints) turns the second visit's start into a few decodes. Cost: ~100 lines in 008-batch and 004-main; no download change; no look change. Measure with `tests/startprof.cjs`.
3. **A nightly measured run on `main`.** Keep pull requests light as the owner wants, but run `budget`, `samepic` and `startprof` once a night on `main` by schedule (`workflow_dispatch` already exists; add a `schedule:` trigger) and post the numbers as a check annotation. Performance regressions are then found within a day instead of never, at zero cost to the daily flow.
4. **A Node-only test layer for pure logic.** `tests/core.cjs` already names the core (imports, levels, SYS, ZONES, VIS, FADE, collision), and seven checks already read the rig under plain Node; `collide`, `ZONES.at`, `LEVELS.at`, the SKIN decoder and the online interpolation buffer need no browser either. A `tests/unit/*.cjs` set run under `node` (seconds, no Playwright) on every pull request gives fast feedback where there is none today.
5. **Widen the `later` chunk.** `tools/later.cjs` already has the coverage; let it mark methods and functions under 300 characters too, and feed it the same coverage from two or three more routes (the bodega, a shop, the station) so a function one route touched is not kept for everyone. Then find the two long tasks before the start with the long-task observer and give them breaths. Together these move a large share of the 2.3 MB start bundle behind the first frame with no change in `src/`. The win is parse and compile time on every visit, not only download.

### B. Do these before the economy or the player count matters (medium payoff, real work)

6. **Server-side money.** Keep everything else client-authoritative, but make cash a ledger in the `Home` Durable Object: the client sends `buy {item, qty}` / `sell`, the server prices it from `data/items.json` (already shipped to the worker's `dist/`) and returns the balance; `/owned` stops accepting an `inv` cash field. One system, one path, as the rules ask; roughly 150 lines in `worker/door.js` and the four client call sites. Without this the $1,000,000 and every shop are decoration.
7. **Cheap sanity on the relay.** In `Block.onMessage`: a speed clamp on `mv` (reject a jump over N tiles per second unless a level/room change), a per-player cap on `puts` rows and `world` writes (or owner-only `world` keys), and a player cap per Block with the next player told the section is full. Each is a few lines; none changes play.
8. **Session cookie set by the worker as HttpOnly** on `/enter` instead of by door.html's JavaScript, and integrity hashes on the two CDN libraries. Small, closes the two obvious holes.
9. **Commit the missing SQL** (players, admins, invite_codes, bug_reports, `join_beta`, the `bugs` bucket policies) under `supabase/` so the row-level security can be reviewed and rebuilt; today it exists only in the dashboard.

### C. Worth doing when a session is in the area (low cost, incremental)

10. **The lamp cube shadow.** It is the biggest single draw cost after the main pass (six faces of the scene every other frame). Through a 240-line filter a 256 cube is indistinguishable from 512; and the pool could take its casters from the CULL cells round the lamp instead of the whole scene. Measure with `perfaudit.cjs`; the owner must see the before/after picture.
11. **One painter kit.** 25 copies of hash/noise and a dozen private `tex()`/`draw()` helpers across builders: move them to 004-main (where `hash3`, `vnoise`, `fbm`, `tex` already live) and have new files use those. Do it file by file as files are touched, never as a sweep (it would conflict with every open branch).
12. **Split `frame()` into SYS phases** the same way: each new piece of per-frame work goes in as a `SYS.add`, and the inline `SYS.go` wrappers are moved out two or three at a time when the file is touched, keeping their order. Not a rewrite.
13. **Allocate NPC self-shadow targets lazily.** 51 × 256² depth targets are allocated; two are used. Allocate on first `SELFSH` pick and keep a pool of four.

### D. Leave alone (honestly assessed, not worth the cost)

- **The module system and the numbered files.** Replacing it with a conventional bundler setup buys readability for humans and loses the order rule, the scope proof and the chunk markers that the current workflow depends on. Not worth it while the project is AI-written and ships daily.
- **The data format.** Int16 JSON + gzipped `.bin` is within 10–20% of what Draco/meshopt would give for these models and needs no loader. Keep.
- **The pinned three.js and the string patches.** Upgrading would mean rewriting every patch for no visible gain. Pin it, keep `SHX`, and treat an upgrade as its own project if ever.
- **The dense code style.** It is a readability cost for humans only; the project's stated audience is the owner's decisions and AI sessions. Changing it would churn every file.
- **Full server authority for movement and combat.** A relay with proximity checks is the right size for an invite-only world; revisit only if public.

### What this review did not measure

Real-GPU frame times (only a software renderer is available here), the start time on a real machine, mobile (there are no touch controls; the game is desktop, gamepad and Quest), and the Supabase row-level security (no SQL in the repo).
